# i18n

Interface text lives in `locales/<bcp47>/<namespace>.json` as i18next JSON v4. Edit `en` only. Weblate writes the other languages. A missing translation falls back to another variant of the same language and script, such as `es` and `es-419` or `pt-BR` and `pt-PT` but never `zh-Hans` and `zh-Hant`, and then to English.

## Adding a string

1. Add it to `locales/en/<namespace>.json` in American English, under a camelCase key named after where it shows, such as `feedback.requestBlocked.rotate`, and word it by the [copy rules](#copy-rules).
2. Run `bun run gen:i18n` so `t()` and `Rich.svelte` accept the new key.
3. Render it with `t("namespace.key", params)` from `$lib/i18n`, or with `Rich.svelte` when it has tags or a component in a placeholder.
4. When a file has no raw text left, add it to `translatedSvelteFiles` or `translatedScriptFiles` in `eslint.config.js`.
5. Commit. The pre-commit hook checks the locale files, regenerates `generated.ts` and stops the commit until you stage it.

## Copy rules

- Use Apple title case only for names: titles that are names or noun phrases, such as “Choose Location” or “No Taps Yet”, section headings, tabs, navigation and landmarks, badges, filter names, chips, toggles and sliders, and picker options.
- Use sentence case for everything else: buttons, menu items, links, error and status titles even when short, titles that are statements or questions (with no period), and all prose.
- Proper names and Grindr feature names keep their capitals in any case, such as Open Grind, Grindr, Right Now and Viewed Me.
- Write curly quotes and apostrophes (“ ” ’), primes for heights (5′11″), a closed en dash for ranges (18–30) and the single-character ellipsis (…).
- End every sentence of a message that has more than one sentence with a period.
- Word a one-time failure as “Couldn’t …” and a lasting state as “Can’t …” or a plain statement. Use “Still can’t …” only after the user retries a lasting state by hand, and keep “Failed to …” for English-only diagnostics.
- Leave out “we”, “us”, “our” and “please”.
- Say “user” for another member’s account (block, hide, report), “profile” for what is shown, and “account” only for your own.

## Message syntax

`{{name}}` is something the app supplies whole, such as a number, a name or an icon. `<name>…</name>` wraps text that translators write, such as a link label. Name tags and placeholders after what they hold, such as `<gridLink>` or `{{menuIcon}}`, never a generic `<link>`. Plurals are `key_one` and `key_other`, picked by `{{count}}`, and text for zero needs its own key.

## Rich text

```svelte
{#snippet gridLink(text: string)}<a href="/">{text}</a>{/snippet}

<Rich key="interest.taps.empty.description" {gridLink} />
```

`Rich.svelte` takes one prop per name in the message. A tag takes a snippet that must render the translated text it receives. svelte-check does not catch a snippet that leaves it out. A placeholder takes a string, `{{count}}` takes a number, and a placeholder outside every tag can take a snippet that renders a component instead. Plain `.ts` code uses `richParts()`.

## Following the language

Text must update when the language changes, so call `t()` where the text is shown. Reapply text that a library writes into the DOM once from an `$effect`, or with `followLocale()` outside a component. Show an error toast that stays open with `showPersistentErrorToast()`. Map enum ids to message keys, and wrap the map in `translatedLabels()` where code reads labels by id. Its labels translate on each read, so copy them only where they are shown.

Diagnostics such as console output and copied error details stay English. To reuse a message there, render it with `sourceText()`, which always returns the English text.

## Choosing the language

The app shows the language chosen in the app, then the first system language a catalog matches, then American English. The choice is the `language` preference, a BCP 47 tag that survives signing out. Until one is stored, the language follows changes to the system list. `$lib/platform/app-language.ts` reads the system languages, secondary ones included, from the native `app_languages` command, and from `navigator.languages` in a browser or when the native read fails. Where the system has a per-app language setting, it and the in-app choice update each other: `$lib/platform/language-sync.ts` tells which side changed from `languageSync`, the per-app value last seen. Android 13 and later and the installed macOS app have such a setting. Windows, Linux, older Android and a macOS `tauri dev` run report only the system list, so a choice made in the app stays until it is changed there. A stored choice that the build no longer offers is cleared. In dev and screenshot builds, `?locale=` pins any tag a catalog matches for the session and is never stored.

The Language row in the app settings opens a page that lists the offered languages. Each shows its English name over its name in itself, both from `language-names.ts`, a table kept in alphabetical order of the English names. A new directory needs a row there, and `language-names.test.ts` fails without one. Picking a language loads its catalog and switches at once. Screenshot builds load every catalog but list the languages a release lists, from `listed-languages.ts`, and mark American English while a pseudo-locale or an unshipped catalog shows.

## Matching languages

`matcher.ts` picks the catalog for a BCP 47 tag the way CLDR and browsers do, with only the CLDR data the directories need written into it. A tag without a region means its CLDR default: `pt` is Brazilian, `es` is Spain Spanish, `zh` is Simplified and `en` is American English. Regional variants follow CLDR's parent locales: Spanish of the Americas uses `es-419`, Portuguese outside Brazil uses `pt-PT` and English of the Commonwealth and Europe uses `en-GB`. A match never crosses languages, except that Norwegian and Nynorsk use Bokmål, and a tag in another script than the language's usual one, such as `hi-Latn`, matches nothing. POSIX names such as `de_AT.UTF-8` read as `de-AT`, and a pseudo-locale matches only its own tag. `getLocale()` returns the tag as given, such as `es-MX`, which sets `lang` and the regional formats, and `getCatalogLocale()` returns the catalog that supplies the text, such as `es-419`. Plural forms follow each catalog's own language. A new regional directory may need a parent or default-region entry, and `matcher.test.ts` checks that each directory is reached by its own tag and by its bare language.

## Shipping a language

Release builds offer English and the directories listed in `shipped.json`, and leave every other catalog out of the bundle. Dev and screenshot builds offer every directory and the pseudo-locales. Add a directory to `shipped.json` only when its own catalog has every message translated, without counting text a sibling variant would fill in, and when the app shows it correctly: its fonts, wrapping, truncation and layout. Right-to-left languages cannot ship yet. Then run `bun run gen:i18n`. It regenerates `shipped-files.ts` and the language lists for the per-app language settings of Android and macOS: `locales_config.xml` and `CFBundleLocalizations` in `src-tauri/Info.plist`, whose other keys stay as they are. `bun run check:i18n` warns about a shipped language that lacks a message, and `bun run check:i18n-release` fails on it. `bun run build`, which `tauri build` runs for every release, runs `check:i18n-release` first.

## Native strings

Text that Android draws itself, such as notifications, notification channel names and the warning about an outdated WebView, comes from the same messages. `android-strings.json` maps each Android string resource name to a message key, and the message can have placeholders but no tags or plural forms. `bun run gen:i18n` writes `src-tauri/gen/android/app/src/main/res/values/strings.xml` in English and a `values-<qualifier>/strings.xml` for each shipped language, so a Gradle build needs no Bun. Never edit them by hand, and reference a resource from Kotlin only once the manifest maps it. Placeholders become `%1$s`, `%2$s` and so on in the alphabetical order of their names, so a translation can reorder them and rewording the English never renumbers them. Kotlin passes the values in that order, each as a string. Names that never translate, such as `app_name`, live in the hand-written `res/values/brand.xml`. `bun run check:i18n` fails when the English file is out of date, a shipped language has no file, or a file belongs to a language that is not shipped. It only warns about an out-of-date translated file, because Weblate's pull requests do not regenerate it, and `check:i18n-release` fails on it, so run `bun run gen:i18n` and commit the result before a release.

## Regional formats

Words follow the app's language. Numbers, dates and times follow the system's regional settings: the 12- or 24-hour clock and its hour padding, decimal and grouping separators, and a numbering system the user chose. Dates use the language's variant for the system region when CLDR has one, so their day and month order follows the system, along with that variant's month abbreviations. Without such a variant they keep the language's own order, because reordering would break its grammar. Format with the helpers in `format.ts`, never with a fixed pattern. Plural forms stay on the language. In dev builds, `?regional=de-DE-u-hc-h12` or a JSON snapshot pins the regional settings for the session.

## Changing a string

A new meaning, tag or placeholder needs a new key. To rename a key, lock the Weblate components and merge their pending changes, then run `bun scripts/i18n/rename-key.ts <old> <new>`. It moves the key in every language and rewrites its quoted uses in `src/`.

## Finding raw English

In dev builds, `?locale=en-XA` shows every translated string accented and padded, and `?locale=ar-XB` shows it right to left, so raw English stands out. `e2e/i18n-pseudo.spec.ts`, `e2e/i18n-pseudo-settings.spec.ts` and `e2e/i18n-pseudo-updates.spec.ts` fail when raw English shows on the pages they visit or in the toasts they show.

## Marking keys

`?locale=en-XM` shows English with each message wrapped in invisible markers: tag characters that spell its key, or the base key of a plural form. Formatted numbers and dates carry no markers. `markers.ts` writes and reads them, so a tool can tell which keys a screen shows. Text with letter spacing moves by one letter space per marker, and `e2e/i18n-markers.spec.ts` fails when a marker shows. Builds made with `OPEN_GRIND_DEMO=1 OPEN_GRIND_SCREENSHOTS=1` accept `?locale=` and the pseudo-locales, as dev builds do.

## Screenshots for translators

`bun run gen:i18n-screenshots` builds the demo with `OPEN_GRIND_SCREENSHOTS=1`, serves it on port 5396 and captures the views in `scripts/i18n-screenshots/scenes` into `i18n-screenshots/`. `--skip-build` reuses `build/`, `--view <id>` captures only the scenes that contain that view, and `--out` and `--port` move the output and the server. Each scene drives its views in English in a fresh browser context, and each view is screenshotted and its page and document title are scanned for markers in the same `en-XM` frame. A view with a `scroller` adds a numbered view, such as `settings/app#2`, for each further screen that shows a new key. A view that shows a toast, dialog, menu, sheet or popover over a page that another view captures names that view in `screen`: the view of the same page on the same platform, scrolled alike and numbered if need be, such as `settings/profile#3`, even when the page holds other data. A view with an overlay over a page that no view captures is listed in `scenes/overlays.ts` with the reason instead, and a view that shows overlay keys without either fails, as does a view that names a `screen` but shows no overlay keys, such as one whose toast timed out before its frame. To add a view, add a scene, list it in `scenes/index.ts` and capture it with `--view <id>`.

A scene sets its demo state in `demo` and can pick another shim OS than its display's, Android on phone and macOS on desktop, in `shim`. The shim OS also sets `navigator.platform` in every scene, so keyboard shortcuts follow it on every host. A scene answers, rejects, sequences or holds native commands in `native`. Its steps can change the demo state with `changeScene`, for example to fail the next request, change native answers with `overrideNative`, emit Tauri events with `emitEvent` and pick generated photos and videos with `chooseGeneratedMedia`. The demo state can answer commands (`methodAnswers`) and requests, fail both, album and profile photo uploads included, or leave them `pending`, its `inbox` replaces the demo conversations with seeds that the demo builds into inbox rows and threads, `profiles` changes fields of demo profiles on their pages and grid tiles, `maskedProfiles` answers profiles masked the way Grindr answers one that blocked you, or one you blocked, and `playBuild` shows what only the Google Play build shows. A view that shows a spinner or skeleton on purpose calls `showsLoading`, so settling stops waiting for it. `clippy.avif` has no license, so every run serves a generated placeholder in its place, and a view fails if the real image is served.

`manifest.json` holds `commit`, the `failed` view ids and each view as `{image, sha256, pixelHash, platform, screen, keys: [{key, box, via, top, button, overlay, wraps, clipped, highlight}], ms}`. `screen` is the id of the view that shows the page under the view's overlay, which can be a failed view, and views without an overlay or with one over a page no view captures have none. `image` is `images/<id>.webp`, or `images/<base>.<n>.webp` for a numbered view `<base>#<n>`. `box` is in image pixels, `via` is `text`, `attribute` or `document-title`, and `top` marks an overlay. A `document-title` entry marks a key that the document title holds and the view does not show on the page. Screen readers announce the title on navigation. The entry is `{key, via, top}` with `top` false and nothing else. Only the first screen of a view without a `screen` gets one: its image shows the top of the page that has the title, and leaving numbered views and views with an overlay over another view's page out keeps the manifest small. `button`, `overlay`, `wraps` and `clipped` are left out when false or unknown. `button` is true when the key is the text, or the `aria-label` or `title`, of a `<button>`, an input of type button, submit or reset, or a `[role=button]` element, so the `aria-label` of an icon button counts. `overlay` is on every `top` entry and on no other, and names the nearest overlay that holds the key: `[data-sonner-toast]` is `toast`, a vaul drawer (`[role=dialog][data-vaul-drawer]`) is `sheet`, `[role=menu]` and `[role=listbox]` are `menu`, `dialog[open]`, `[role=dialog]` and `[role=alertdialog]` are `dialog`, and `[role=tooltip]` and `:popover-open` are `popover`, the first that matches in this order. `wraps` and `clipped` only mark `text` keys in views laid out as in English. Before a view switches to `en-XM`, the scene records the boxes of the elements that hold text in English, and a view where those elements or their boxes differ by more than 1 px after the switch, or that is replayed in `en-XM`, gets neither. A numbered view keeps them while it shows only elements that were compared. `wraps` marks text whose rects fall on 2 or more lines, counting the rects of values the message shows in `translate="no"` elements, where rects that overlap by more than half the shorter one's height share a line. `clipped` marks text that its nearest ancestor with overflow other than `visible` cuts: an ellipsis (`text-overflow: ellipsis`) cuts it when the ancestor's scroll width exceeds its client width by more than 1 px, a line clamp when its scroll height exceeds its client height by more than 1 px, and overflow `hidden` or `clip` when the text's rects, each trimmed to the text's line height, reach more than 1 px past the ancestor's padding box on that axis. Text cut on an axis that scrolls, with overflow `auto` or `scroll`, is not clipped. `pixelHash` hashes the captured RGBA pixels before WebP encoding. It cannot be recomputed from the WebP, so compare it only with earlier manifests. Phone images are 840x1600 and desktop images 1920x1200, but a scene can resize its page, as `chat/inbox/selection/collapsed` does at 560x1600, so read each image's size from the image. `highlight` is `{image, sha256, pixelHash}` for a copy of the view at `images/<id>/<key>.webp` or `images/<base>.<n>/<key>.webp`, and at most 3 views of a key have it. A `document-title` entry never has it and takes no part in choosing the views below: the order, the groups and the counts of keys leave it out. A view where the key sits in an overlay stands on its own. The key's other views are grouped by `screen`, or by their own id when they have none, and each group keeps the view with the fewest distinct overlay keys, then the first in the usual order: views where the key sits in an overlay first, then those that show it as text rather than in an attribute, then those with fewer keys of its namespace, then by view id. The first 3 of the kept views in the usual order get the copy. Every scene keeps lossless captures in `.raw/`, the copies are drawn from them after the last scene, and `.raw/` is deleted afterward. The copy draws a hollow `#FFFF00` rectangle edged in black around each place the key shows, or around the element that carries an attribute key, or around what it holds when the element has no box of its own. A failed id also covers every `<id>#<n>`: the run cannot know how many screens an earlier run kept, so an uploader keeps them all. A view fails when its steps throw, a request leaves localhost or goes unanswered, the page throws or an emoji shows, and the later views of its scene fail with it. `settings/app` is captured twice and fails when the two differ in pixels. A view also fails, with its numbered views but not the later views of its scene, when its `screen` names a numbered view the run did not keep or when a highlighted copy of it cannot be drawn. `coverage.json` lists the keys no view showed and visible text without markers, `explanations`, `englishMeasured`, the sorted ids of the views laid out as in English, numbered ones included, and `compositeButtons`, a `{view, keys}` entry for each distinct set of 3 or more keys that a button in the view holds, and never fails the run. A key that only a `document-title` entry holds counts as shown.

Keys no browser screen shows go into `scripts/i18n-screenshots/uncapturable.json` as `{reason, explanation}`, under the key or under a pattern such as `chat.notification.*` that covers every key under `chat.notification`. `reason` tells developers why no view shows the key. `explanation` is one sentence for translators that says where the text appears or why no one sees it, such as “Body of the system notification that the desktop and Android apps show for a received tap, under the sender’s name; the system draws it outside the app, so no screenshot shows it.” Word it by the [copy rules](#copy-rules) and name features as the app does. `uncapturable.test.ts` also holds it to the limits of the Weblate uploader: 10 to 300 characters, an ASCII capital first and a period last, only ASCII letters, digits, spaces, curly quotes and apostrophes and `. , ; : ! ? ( ) / + % { } - … – —`, and no URL or dotted name such as a key or a file name. `explanations` in `coverage.json` maps each key that an entry covers and no view shows, a plural by its base key, to the sentence of the most specific entry: the key's own, then the longest pattern.

`.forgejo/workflows/i18n-screenshots.yml` runs the capture when a push to `i18n` changes the English messages, `scripts/i18n-screenshots` or the workflow, or when started by hand. It keeps the output for 7 days as the `i18n-screenshots` artifact, which the Weblate uploader reads. The screenshots are public: images, videos and map tiles are made during the run, every other request outside localhost is blocked, Chromium resolves no host but localhost and sends what slips past to a local proxy that drops it and fails the view, and the demo data in these builds holds no emoji, real places or real handles.
